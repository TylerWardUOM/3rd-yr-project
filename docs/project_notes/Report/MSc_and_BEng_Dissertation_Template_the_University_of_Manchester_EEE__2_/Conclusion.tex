\noindent
This section summarises the extent to which the project objectives were achieved and identifies the main directions for future work.

\subsection{Conclusions}

This project designed, built, and evaluated a low-cost modular haptic rendering system combining a two-degree-of-freedom input device with custom simulation and visualisation software. At prototype level, user motion was sensed, transmitted to the host, coupled to a virtual environment, and returned to the device as actuator torque commands. The architecture also separated hardware communication, haptic rendering, physics simulation, and visualisation.

The most important technical result is that bounded haptic interaction was still achieved in the tested cases despite a measured round-trip communication delay of 15.60--15.67\,ms. This latency prevents the system from being described as a true 1\,kHz end-to-end haptic loop, even though selected local subsystems achieved nominal 1\,kHz operation and host-side processing latency remained low. The results therefore separate two claims: the host was fast enough to compute and publish rendered-force commands locally, but the physical interaction was limited by delayed state freshness, actuator capability, transmission behaviour, and the absence of calibrated force or current sensing.

The project met the main evaluation objectives defined in Section~\ref{sec:introduction}. The sub-£200 interface was constructed with joint sensing and motor command capability, although final force-feedback validation was limited to one actuated joint after actuator failure. Communication tests demonstrated nominal 1\,kHz packet generation and quantified packet rate, burst-like delivery, packet loss, out-of-order events, round-trip latency, and host-side processing delay. Motor-enabled tests showed bounded contact and consistent logged force-command behaviour in the tested interactions. Safety behaviour was supported by host-side force-command saturation, embedded torque limiting, torque slew-rate limiting, and watchdog torque removal.

The project therefore demonstrates an integrated low-cost haptic rendering pipeline, but it does not demonstrate calibrated physical force output or full two-axis force-feedback performance. Its strongest contribution is the evidence that useful bounded contact can be obtained on constrained hardware with a delayed communication path, provided that the system is designed around damping, saturation, latest-snapshot communication, and actuator-side safety limits. The main insight is that high-rate local computation and an accurate command-side force model are not sufficient on their own: communication delay, actuator capability, transmission behaviour, and the absence of calibrated physical sensing jointly determine achievable haptic fidelity. Stronger claims about haptic transparency, quantitative force fidelity, or training effectiveness would require lower-latency contact control and calibrated physical sensing.

\subsection{Future Work} \label{sec:future_work}

The first priority is to reduce effective actuator-side latency. Future work should compare the current ST-Link virtual COM pathway with lower-latency links such as direct UART through a dedicated USB--UART bridge, native USB transfer, CAN bus, or Ethernet-based communication. This comparison should use the same packet sequence numbering and timing logs developed in this project so that mean latency, jitter, burst delivery, dropped packets, and stale-state events can be compared directly. The aim would not simply be higher throughput, but lower and more predictable state age at the instant the actuator command is applied.

Future work should also move more contact behaviour closer to the high-rate loop. A stronger multi-rate architecture would maintain a reduced local contact model at 1\,kHz, while slower physics, rendering, or application layers update the broader scene. The local model could store the currently contacted surface, proxy state, penetration history, and tangential motion, instead of re-computing contact from delayed snapshots each cycle. Moving the proxy/contact evolution onto the embedded controller would further reduce dependence on delayed host--device exchanges, at the cost of simplifying the embedded contact model using local planes, SDF patches, virtual fixtures, or reduced contact geometry. This would make the system closer to established proxy or god-object rendering approaches while preserving the modular host simulation.

Hardware development should focus on calibrated sensing and restored two-axis actuation. Phase-current sensing and external force measurement would allow quantitative physical force validation and more accurate torque control, while a lower-backlash transmission such as a capstan drive would reduce belt slip. With calibrated sensing, the logged rendered-force command could be compared against actual output force rather than only command-side behaviour. This would support identification of actuator bandwidth, friction, backlash, and torque constant errors, and would allow the controller to be tuned against physical force fidelity rather than perceived contact quality alone.

Control development should then use the improved sensing and transmission model to move beyond the conservative damping-based prototype. Incorporating task-space dynamics would allow the manipulator inertia and kinematic mapping to be compensated more explicitly during interaction. More advanced impedance or admittance control could also be tested once physical force or current feedback is available. These changes would need to be introduced alongside passivity-aware limits, because increasing stiffness without reducing delay or adding damping would reintroduce the stability risks identified in the discussion.

Further software work should improve contact continuity and evaluation. Constraint-based proxy updates, smoother contact entry/release, velocity-state blending, and stale-command rejection would address force-direction inconsistencies during large penetration. Integration with robotic simulation platforms such as NVIDIA Isaac Sim, MATLAB/Simulink, or ROS-based environments would make it possible to test more realistic manipulation scenarios while keeping the low-cost device as the physical interface. Finally, force measurement, user studies, and task-based metrics should be used to assess whether the system improves training outcomes rather than only demonstrating technically bounded haptic interaction.
